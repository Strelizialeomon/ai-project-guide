# 需求梳理

`AGENTS.md` 第四节的展开。开工前读。

## 为什么非做不可

**需求没定死就写代码 = 照着没定稿的图纸施工。**

业务人员描述需求时天然会漏东西——不是他藏私，是他**不知道自己不知道**。你没问到的地方，你会自己「补」一个合理的默认值。补出来的通常不是他想要的，而且要到很后面才暴露，那时候返工的成本已经翻了几倍。

---

## 一、装 superpowers

从**官方插件市场**装 `superpowers`。

⚠️ 具体命令按你当前版本自己去查，别照抄任何旧写法——插件市场的装法会变，照抄旧命令是最常见的翻车点。

装好后确认能用，再用它下面的 brainstorming 能力。

---

## 二、用 brainstorming 把想法问成需求

用户开口通常是一句模糊的抱怨：「每周催周报烦死了」。brainstorming 的作用是**把这句话问成一份写死的需求**。

### 提问的规矩

**一次问一个。** 别甩一串问题让他做卷子——他答不过来，就会随便答，随便答比不答更糟。

**能自己查、自己判的，先查先判。** 别拿问题占位。他电脑上装了什么、公司有没有现成在用的系统，这些你自己能摸清楚的，别问他。

**只把真正只有他能拍板的留给他**：

- 要什么、不要什么
- 给谁用、谁能看
- 什么算做得好

**给推荐，别把他当考官。** 你发现方案有洞、或者你不同意他的说法时，把思考做完再交——给出「最强反方 + 你的判断 + 推荐理由」，让他否决。**不要**拆成一串问题车轮战甩回去。

### 什么是「真正只有他能拍板」的

拿不准的时候用这条试：**这个问题，我能不能从代码、从常识、从现有环境里判出来？**

- 能 → 自己判完，告诉他结论就好
- 不能 → 才是他的

## 三、⛔ 走到需求为止，不要接着排计划

superpowers 里有个环节叫 **writing-plans（排实施计划）——不要调它。**

### 为什么

**需求刚谈完就排施工计划，等于照着还没定稿的图纸开工。**

两件事会同时发生：

1. **业务场景里需求天天在变。** 今天排的计划，下周就作废。你花在计划上的功夫全白费。
2. **更糟的是那份错觉。** 一份排得整整齐齐的计划，会让你和用户都以为「已经想清楚了」。真正没谈拢的地方，会被计划的整齐盖住——**越整齐，盖得越严实。**

### 终点在哪

**这套流程的终点，是一份用户点头确认的需求，不是一份实施计划。**

确认完，直接动手，一边做一边让他看。

## 四、一份写清楚的需求长什么样

写完之后**逐条对一遍**，缺哪条补哪条：

| 要有 | 说明 |
|---|---|
| **给谁用、解决什么麻烦** | 一句话说清。说不清就是还没想明白 |
| **用户会做的每一步** | 点哪里、看到什么、下一步是什么。用他的动作描述，不用技术词 |
| **要记住什么** | 谁、什么时候、什么状态。这一条直接决定要不要数据库 |
| **要看的数据从哪来** | 谁产生、怎么进系统、多久更新一次。他要看板 / 监控 / 报表时必须问，见 `数据地基.md` |
| **什么情况算出错、怎么处理** | 最常见的是漏这条。没有它，出错时没人知道该怎么办 |
| **怎么验收** | 他能亲手点出来的几条。**最容易漏，也最要命** |

### 最后一步：让他读一遍

写完了别自己点头就算数。**让他读**，问他一句：

> 这几条，哪条跟你想要的不一样？

**他点头，才开工。**

## 相关

- 他说要「看板 / 监控 / 报表」 → 先读 `数据地基.md`，那个数从哪来是需求的一部分
- 反过来，需求里说「这个数人工填」 → 把「谁填、多久一次、漏了谁发现」问完再往下走
- 判断该上哪几层 → `四层模型.md`
