# 数据地基

`AGENTS.md` 第三节的展开。用户提「看板 / 监控 / 报表 / 驾驶舱」，或者任何「我要看到某个数」的时候读。

## 先说这条链

**有人做了个动作 → 动作被记下来 → 被汇总、被计算 → 存下来 → 才轮到你看**

这叫**数据流转**。业务方只会跟你提最后一段——「我要看到 xx」。前面几段他从没想过，因为**看不见的东西不会被想起来**。

**这条链和盖楼一样：地基埋在土里，没人看见，但亭台楼阁全压在它上面。**

一个生活化的比方：

> 看板是水龙头。业务方永远只提水龙头——「我要这儿出水」。
> 但没人问：水是接了自来水管，还是每天有人拎水桶往里倒？
> **如果是拎水桶，水龙头再漂亮，水质取决于拎水那个人今天心情如何。**

## 第一环：入口

「这个数从哪来」只有三种答案。**每种都有躲不掉的坑**，你要主动告诉用户——他不知道有坑，就不会觉得这是个需要拍板的事。

### 一、人工填

人在页面上一条条填，或者交 Excel 给你导进去。

**躲不掉的坑：**

| 坑 | 为什么躲不掉 |
|---|---|
| **漏填没人发现** | 少一条记录，看板上完全看不出来——分母变小了，比率反而可能更好看 |
| **事后补记** | 世界卫生组织的规程里把这句写得很直白：「事后补记制造了时间上的假象。」 |
| **填的人有动机** | 这个数一旦跟他的考核挂钩，就会往好里走 |

**「填的人有动机」这条最要命，因为它是理性的，不是道德问题。**

真实案例：某注塑企业花二十多万在车间门口做了块三米宽的 LED 大屏，显示设备综合效率、订单达成率、良品率十几个指标。屏上「设备综合效率 87%」是班组长每天下班前手工填的。老师傅原话——

> **「差不多就行呗，填低了扣奖金，谁会往低了写？」**

**所以只要入口是人工填的，你必须在同一句话里问出三件事：**

1. 谁填？
2. 多久填一次？
3. **他漏填了，谁会发现？怎么发现？**

**第三个答不上来，这个看板就已经是假的了。**

**还有一个该做的动作**：把校验规则做在**录入的那一端**。中石化某油田的数据治理专项就是这么干的——他们管这叫「捉虫」，专查「错填、漏填、重复、不一致、不规范」，做法是**迭代优化前端填报校验规则，卡住新增数据入口**。

**为什么要在源头卡**：一份实测研究（PLOS ONE，2012）比较了两种录入方式——**单次录入每 1000 个字段错 0.370 个，双人独立录入降到 0.046 个**。录入环节的错误，越往下游越难发现、越贵。

### 二、外部送过来

别的系统推过来，或者我们定时去拉。

**躲不掉的坑：**

| 坑 | 现实里长什么样 |
|---|---|
| **对方根本没有接口** | 老系统没开放接口，或者对方是别的部门 / 别的公司，不归你管 |
| **有接口但要审批** | 走流程几周，还可能被拒 |
| **字段对不上** | 两边的「状态」不是一回事；两边的编码规则不一样 |
| **失败没人管** | 推送半夜断了，第二天没人知道，看板上就是昨天的数 |
| **重复和乱序** | 重试会让同一条记录来两次；网络延迟会让后面的先到 |

**「字段对不上」这条要特别小心：坑往往不在字段名，而在字段含义。**

同一个 `status`，在一个系统里是「业务处理状态」，在另一个里是「账号启用状态」，在第三个里是「审核状态」。字段名可以映射，含义得人去对。

**动手前必须去摸**，摸完告诉用户三种结论之一：

- 这条路能走通
- 要走通得先解决 A 和 B（说清是谁的活、要多久）
- 走不通，只能人工

**别假设「对接一下就行」。** 这是最容易拍脑袋的地方。

### 三、系统自己产生

我们做的这个东西自己记下来的。

**最靠谱**——数据在产生的当下就被系统记下，不经过人手转述。

**但代价最高**：等于要把业务流程真的搬进系统。用户原来在纸上、在微信里、在脑子里跑的流程，现在得变成系统里的步骤。

**而且这里有个前提**：得有人真的在用这个系统。系统做出来没人用，等于入口还是空的。

### 第四种，也是最贵的：没有入口

业务说：「我从别的系统里捞出来，填到你这儿。」

**这不是方案，这是把人工成本藏起来了。**

- 他每周要花多少时间？没人算过。
- 他休假了怎么办？没人想过。
- 他填错、漏填了，谁发现？没人管。
- 他离职了呢？这条链子直接断。

**这一条必须当面说破，别默默接受。** 说破之后通常有三条路：

1. 这个数其实可以自动取，去把接口打通
2. 这个数先别看了（很多时候它并不真的需要每天看）
3. 确实只能人工，那就写进交付说明：「这个数依赖某某每周手工维护，他不在就更新不了」

## 第二环：处理

这一段要问出来的是**口径**。

**同一个词，两个人理解不一样——这是最常见的翻车。**

「良品率」这三个字，至少藏着四个问题：

- 是当天的，还是当月的？
- 分母是全部产量，还是只算已经检验完的？
- 返修后合格的，算不算良品？
- 试产的那批算不算？

**不写下来，做出来的数一定有人不认。**

### 怎么算「写下来了」

一张表，一个指标一行，**这几列缺一不可**：

| 列 | 举例 |
|---|---|
| 指标名 | 良品率 |
| 怎么算 | （检验合格数 ÷ 已检验数）× 100% |
| 从哪来 | 检验记录表的「结果」字段；产量表的「批次」字段 |
| 多久更新 | 每天凌晨 |
| **谁负责** | 质检部张三 |

**「谁负责」这一列最容易被省，但它是唯一能在出问题时找到人的东西。**

这不是我们自创的要求——阿里云 DataWorks 官方文档里，定义一个「原子指标」必须填的就有：业务口径、业务分类、业务过程、**负责人**、计算函数、数据单位、是否去重。

**更严的一个参照**：美国联邦医保局（CMS）的指标规范要求，一个指标必须先写清 **目标人群 → 分子 → 分母 → 分母排除项 → 分子排除项 → 例外 → 计算逻辑**，而且明确要求**用文字而不是代码描述分母**。

小项目不用做到这么重，但**「分子是什么、分母是什么、排除了什么」这三样，一定得用说人话的方式写下来**。

## 第三环：存放

这一段要问出来的是**多久更新一次**。

| 他说 | 意味着 | 什么时候真的是这样 |
|---|---|---|
| 「要实时」 | 最贵 | 只有当「看到之后要马上动手」时才值得 |
| 「每天 / 每周更新就行」 | 通常够用，便宜得多 | **绝大多数看板都在这一档** |
| 「我想看就刷新」 | 最便宜 | 数据变化很慢的场景 |

**听到「要实时」，先反问一句：「你看到之后要马上做什么？」**

多数时候答案是「也没什么，就是看看」——那就用不着实时。**为实时而实时，是白白花钱。**

### 如果这个数最后是从 Excel 来的

现实里很常见：业务其实全靠 Excel，看板只是把 Excel 画得好看点。

**这种做法的硬边界，厂商官方文档里写得很清楚：**

- **改结构会崩**：改列标题、删列、调整列顺序，甚至只是把列名从 `Age` 改成 `age`（大小写变了）——**都会导致依赖这些列的图表配置丢失**。安全的操作只有两个：在已有列下面追加行、在表格末尾追加新列。
- **不是实时**：微软官方文档写明，从 OneDrive / SharePoint 导入的 Excel，服务**大约每小时**才检查一次更新。而且 **Excel 不能作为「直连查询」的数据源**，只能导入。

**所以「Excel 当数据源」这条路能走，但必须跟用户说清两件事**：表格结构不能动；数据最多每小时更新一次。

## 第四环：呈现

到这一步才轮到「看板长什么样」。

**但先问一句：「你多久看一次？看到之后做什么？」**

这一问能筛掉很多东西。如果答案是「每周开会看一眼」，那可能根本不需要一块大屏——**一份每天早上推送到手机上的数字，比一块没人看的大屏有用得多。**

真实对照：某经营驾驶舱项目花 40 万做了 40 多个指标、10 块大屏页面，**上线一年累计被打开 137 次**，其中 60 次发生在验收后两周。后来他们把指标砍到 12 个，每天 8:30 推送给 10 个负责人——**这张日报的使用率是原来那套驾驶舱的 40 倍**。

另一家年营收数百亿的制造集团，大屏数据直连业务系统、实时更新、维度齐全，**上线后每月访问量几十次**。复盘的判断是：它「不在领导的工作节奏里」——看大屏需要专门去看，而领导日常是会议、汇报、批件。

**这两个案例说的是同一件事**：呈现这一环的价值不在好看，在**它有没有长在人的动作上**。

## 把它整个走一遍

用户说：**「我要个看板，能看到各车间每天的良品率。」**

往上问：

| 问 | 答 | 判断 |
|---|---|---|
| 良品率凭什么长出来？ | 一条条检验记录 | — |
| 检验记录凭什么长出来？ | 质检员检完录进系统 | — |
| 他为什么愿意如实录？ | …… | ⚠️ **这里可能就是断点** |
| 录漏了怎么办？ | …… | ⚠️ **第二个断点** |

**问到这儿你才发现：这个看板真正的风险不在图表选型，在「质检员愿不愿意如实录」和「漏录了谁发现」。**

这两条不解决，看板做得再漂亮也是假的。**这就是为什么要往上问——它会把你带到真正的施工面上。**

## 什么时候可以「反过来做」

**这条链子本来就在、而且结实的时候，从「呈现」那头开始做是对的。**

系统里本来就有数、接口已经通了——看板只是给它开个窗。这时候先做看板完全没问题，好处还很大：

- **看板是界面，用户能最快给你反馈。** 他看着一个真东西说「这个指标没意义」，比对着文档说要准得多。返工一个图表，比返工几十个上游转换便宜得多。
- **它能逼出指标口径。** 要画那个图，就必须先把「分母是什么」定下来。

业界管这个思路叫**「反过来做」**，顺序是：先定用户看到什么 → 再定指标口径 → 再定怎么加工 → 最后定怎么存。

**所以这条原则不是「什么都得从最底层开始建」，是「先弄清链子在哪、断没断」：**

| 链子的状态 | 怎么做 |
|---|---|
| 已经存在且可靠 | 从呈现开始，快 |
| 不存在、或不可靠 | 先把链子接上，再回来做呈现 |
| **源头数据本身就不值得建** | **该取消的不是地基，是整个项目** |

最后一行也是行业里的成熟判断：数据仓库教科书的作者明确写过——如果做数据剖析发现源数据烂到撑不起业务目标，**这个项目就该被取消**，而不是硬做。

### 重型的做法也不是「一次建完」

有人会担心「那是不是要先把整个数据仓库建起来」。**不是。**

同一批教科书作者主张的是**一次做一个业务过程**，按需增量补——不是先建一个完美的大仓库再开始做报表。

追求「先建一个完整地基」的另一个极端，同样会失败：项目做半年没有产出，业务方等不及，回去继续用 Excel。

## 反方意见（一并记下）

**有一条反面观点必须知道，因为它是从最权威的那一方来的。**

Gartner 2024 年的判断是：到 2027 年，**80% 的数据与分析治理举措会失败**，原因是「缺乏真实或人为制造的危机」。分析师的原话是：「一个不能支撑优先级业务成果的数据治理项目，就是失败的。」

**这话的潜台词是**：别先做一个大而全的治理工程——先找一个真实的业务痛点（一次看板需求就是），围着它做。

**这条和我们的原则不冲突，反而是同一条：**

- 「先弄清链子在哪」= 别盲目建大工程
- 「围着一次真实的看板需求建」= 从最小的那条链子开始接

**真正要防的，是两头都走极端**：既不先建一个完美的大仓库，也不跳过链子直接做看板。

### ⚠️ 一个流传很广、但**查不到出处**的数字

**「70% 的 BI 项目失败」——这条不要引用。**

多个来源都把它归给 Gartner，但**没有一家给出报告名或链接**，而且各家说的年份互相矛盾（2012 / 2017 / 「十年前」）。行业机构 TDWI 自己也说过，失败率估计从 **30% 到 75%** 不等，**区间这么宽说明口径根本不一致**；TDWI 2011 年一项 600 多人的调研结论甚至是「很少 BI 项目失败」。
