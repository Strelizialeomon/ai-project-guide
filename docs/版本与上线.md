# 版本与上线

`AGENTS.md` 第七节的展开。功能写完、要放进正式版本或要上线时读。

## 一、为什么要有这一节：拍板不等于用上

一个功能从他开口到同事用上，要走完这条链：

**需求拍板 → 在本地优化版本里写完 → 他亲手点过、说「做完了」 → 放进正式版本 → 他说「上线」 → 发布 → 线上核过 → 同事用上**

他只看得见两头：开头他拍了板，结尾同事用上了。**中间那一段他看不见。**

所以两件事一定会发生：

- **他会把「拍板了」「AI 说写完了」当成「同事已经能用了」。** 他不知道后面还有路。
- **中间那段里的 git 动作，只要被当成问题甩回给他，链子就停在那。** 他答不了，也不知道自己该答。

这一节要解决的就是这两件事：**中间那段你走完，走到哪一步都用他听得懂的话告诉他。**

⚠️ 只有他自己用、只在他电脑上跑的小工具，没有「上线」这回事——链子到「他说做完了」就结束，只问第一句就够了。

---

## 二、一次真实的翻车

某财务项目，一位业务同事收到两条同事反馈，跟 AI 一起把需求问清楚、当场拍了板。AI 把它们拆成几件事：三件把代码和测试都写完了，传到了公司的代码仓库，开了三个合并申请；还有一件只写了「另开」。

**其中两个申请的最后一句是：「未合并，等你点头。」** 第三个没写这句，也一样停在那里，没人去合。

结果：线上还是前一天的版本，提反馈的同事什么都没看到。

埋在里面的还有四个坑，**每一个都是 git 的事，他一个也判断不了**：

1. **后两个申请是叠在第一个上面开的**，都夹带了第一个的改动。他只要批了后两个里的任何一个，第一个就会被悄悄一起放进正式版本——下一次上线就跟着上去。
2. **后端测试里需要数据库的那部分，在他电脑上全部跳过了**——电脑上没装数据库。说明里写着要到服务器上补跑，没人补。
3. **「另开」的那件停在了半路**：引用的那份决定记录压根没写出来，也没有人接着做。
4. **提交署名是电脑的默认名字**，事后看不出是谁做的。

更早一次，他自己在网页上点了合并。那个功能后来是技术负责人发另一个版本时被**顺带**带上线的。

**没有一个环节是他偷懒。** 是 AI 把只有它懂的事，交给了一个不懂的人去决定。

## 三、两份版本：怎么跟他讲

### 跟他说的

| 说法 | 意思 |
|---|---|
| **本地优化版本** | 正在改的那份。只在他自己电脑上能点，同事看不到。每个功能各一份，互不影响 |
| **正式版本** | 大家共用的那份。上线之后，同事看到的就是它 |
| **上线** | 把正式版本发出去，同事刷新就能用 |

需要打比方的时候，按他的业务现场现打。比如对做财务的人：「本地优化版本像你桌上的草稿，改坏了也不影响别人；正式版本像已经归档的那份，大家照它办事。」

### 给你的对照（别说给他听）

| 他听到的 | 实际是 |
|---|---|
| 本地优化版本 | 从**最新**主干开出来的功能分支，一个功能一条 |
| 正式版本 | 主干（通常叫 `main`） |
| 放进正式版本 | 合并进主干 |
| 上线 | 发布到服务器（各项目的发布方式不同，照项目自己的规矩） |

### 开工前先查清：放进正式版本会不会自动上线

有的项目要另外发布一次才上线；有的托管平台**一合进主干就自动发布**。开工前先查清是哪种：

- **要另外发布** → 两句话分开问（见本篇第四节）。
- **一合进就自动发布** → 两句话合成一句：「这个功能做完了，现在就上线吗？」否则他答「做完了」就等于答了「上线」，第二句成了摆设。

### 每个功能一份，不许叠

**每个本地优化版本都从最新的正式版本开，不许开在另一个还没放进去的功能上面。** 叠着开，就是上面翻车里的第 1 个坑：他以为自己只放进去了一个功能，实际带进去两个。

功能 B 真的离不开功能 A 时，用业务话跟他说：「B 要等 A 做完才能开始」——然后先把 A 走完。

## 四、两个问题：什么时候问、怎么问

### 第一问：「这个功能做完了吗？」

这里的「做完了」**只指这个功能改好了**，不等于同事能用。

**问之前，你自己先过这四条。** 有一条不满足，就还没到问的时候：

1. 他已经在自己电脑上**亲手点过**需求里的验收项（见 `docs/验收与交付.md`）
2. 测试**全部跑通**——「跳过」不是「通过」。缺东西导致跳过，先装齐再跑；真装不上，明说哪部分测不了（见本篇第七节）
3. 你自己先点过一遍，别让他当第一个发现问题的人
4. 这个功能要不要改数据库结构、改服务器配置、改线上数据？要的话，现在就告诉他上线前得单独讲清（见本篇第八节）

问的时候，把后半句说出来——让他知道「做完了」之后同事还看不到：

> 「这个功能做完了吗？做完了我就放进正式版本。放进去同事还看不到，上线之后才看得到；下一次上线会带上它，不管是谁点的上线。另外你刚才点的是样例数据，数据多了会不会慢，要上线后才看得出。」

他说做完了 → 你把它放进正式版本，**然后马上问第二句**。

他说还没有 → 问他还差什么，接着改。

### 第二问：「现在上线吗？」

**你主动问，别等他开口。** 他不知道还有这一步——这正是翻车里「等你点头」的反面。

问的时候带上你的建议，并说清两件事：

- **上线后同事会看到什么变化**，尤其是会不会影响他们手上正在做的事
- **这次会不会顺带捎上别人做完的功能**（正式版本是大家共用的）

他说上 → 你发布，发完**自己去线上核一遍**，再回报「上线了，同事刷新就能用」。

他说先不上 → 停在正式版本。下次汇报时提醒他：「日报锁定还在正式版本里等上线。」

### 话术对照

| ❌ 别这么说 | ✅ 这么说 |
|---|---|
| 「MR 已提交，未合并，等你点头。」 | 第一问：「日报锁定在你电脑上能点了，你试一下：昨天的日报点不动了。这个功能做完了吗？做完了我就放进正式版本——放进去同事还看不到，上线之后才看得到。」 |
| 「要打 v1.0.2 的 tag 吗？」 | 第二问：「日报锁定已经放进正式版本了。现在上线吗？我建议下班后上：上线后同事就不能补昨天的日报了，白天上可能正好有人在补。这次还会顺带把小李做完的首页提醒一起带上。」 |

## 五、你全包的那些事

下面这些**都不拿来问他**：

- **署名**：提交用他自己的名字和工作邮箱，不用电脑默认名。先从他电脑上已有的账号信息里取，取不到才问他一次「你的工作邮箱是哪个」——这是问他是谁，不是问 git
- **开版本**：每个功能一条分支，从最新主干开
- **对齐**：别人放进正式版本的东西，及时同步到他正在改的版本里
- **放进正式版本**：他说「做完了」之后的合并，以及合并前的最后一次全量测试
- **冲突**：纯技术层面的冲突自己解决
- **发布、核对、回滚**：照项目的发布规矩走
- **收尾**：放进正式版本后，清掉用完的分支

### 两句话之外，唯一要问他的：改法打架

两个人改了同一处，而且**改法在业务上互相矛盾**——这不是技术问题，是业务问题，得他（或他们俩）拍板。

用业务话问：

> 「小王也改了日报：他的是过了零点就锁，你的是第二天中午才锁。留哪个？」

**不许问「有冲突，怎么处理」。** 他不知道冲突是什么，只能随便选一个。

## 六、「同事用不用得上」只用三句话报

- 「还在你电脑上，同事看不到。」
- 「已经放进正式版本，等上线。」
- 「上线了，同事刷新就能用。」

**只要汇报涉及某个功能走到了哪一步，就落在其中一句上。** 一次动好几个功能时，逐个功能各落一句。

他最容易犯的错，就是把第一句听成第三句。所以**第一、二句里「同事看不到 / 等上线」这几个字不许省。**

这三句不取代 `AGENTS.md` 第六节的「成了 / 没成 / 哪步跳了没做」——那个报的是活干得怎么样，这三句报的是同事用不用得上，两样都要报。

---

## 七、没人替他看代码时，守门的是什么

他看不懂代码，也没有技术的人替他审。守门的只剩两样：**测试，和你自己。**

- **测试必须跑全。** 在他电脑上跑、在服务器上自动跑都行，但得全。缺数据库、缺工具，你先装齐——这是 `AGENTS.md` 第一节「工具装好了没」的延续。**跑不全又不说，比没测更糟**：他会以为测过了。
- **真装不上，明说。** 「这部分测不了，原因是……」——让他知道这次是带着这个风险放进去的，而不是把跳过当通过、闷头往下走。
- **他点的是样例数据。** 他在自己电脑上看到的多半是空数据或样例数据；数据一多才冒出来的问题（列表几百条、页面变慢），上线后才看得出。问第一句时告诉他，上线后你自己先对着真实数据看一眼。
- **上线后你自己去线上核。** 别等同事报错才知道。
- **出事了你主动说、主动回滚。** 先退回去，再告诉他发生了什么、影响了谁、怎么避免下次。

⚠️ 这不是银弹：测试只能拦住写过测试的地方，样例数据也替代不了真实数据。没人审代码，意味着这两处漏掉的毛病会直接上线——**所以回滚要快，出事要早说。**

---

## 八、退不回去的事，单独讲清再上

下面这些**做错了很难退回去**，不能混在一句「上线」里带过去：

- 改数据库结构
- 改服务器配置
- 直接改线上的数据

遇到了，上线前单独跟他讲清楚三件事：

> 「这次上线要改一下数据库的结构：给日报加一列『锁定时间』。万一出错，已有的日报可能读不出来；我会先备份一份，出错就恢复。可以吗？」

他点头了再动。

项目规矩写了这类事要找技术负责人的，照项目规矩找人配合，并跟他说一句「这个上线要技术那边配合一下，我已经去找了」；项目没写，就由你照上面的做。

---

## 九、一句话总结

**「做完了」「上线」这两句他说，其余都是你的事；每次开口，都让他知道同事现在用不用得上。**
