# 版本与上线

`AGENTS.md` 第七节的展开。功能写完、要放进正式版本或要上线时读。

## 一、为什么要有这一节：拍板不等于用上

一个功能从他开口到同事用上，要走完这条链：

**需求拍板 → 在本地优化版本里写完 → 他亲手点过、说「做完了」 → 放进正式版本 → 他说「上线」 → 发布 → 线上核过 → 同事用上**

他只看得见两头：开头他拍了板，结尾同事用上了。**中间那一段他看不见。**

所以两件事一定会发生：

- **他会把「拍板了」「AI 说写完了」当成「做完了」。** 他不知道后面还有路。
- **中间那段里的 git 动作，只要被当成问题甩回给他，链子就停在那。** 他答不了，也不知道自己该答。

这一节要解决的就是这两件事：**中间那段你走完，走到哪一步都用他听得懂的话告诉他。**

---

## 二、一次真实的翻车

某财务项目，一位业务同事收到三条同事反馈，跟 AI 一起把需求问清楚、当场拍了板。AI 把代码和测试都写完了，传到了公司的代码仓库，开了三个合并申请。

**三个申请的最后一句都是：「未合并，等你点头。」**

结果：线上还是前一天的版本，提反馈的同事什么都没看到。业务同事那边，事情已经「做完了」。

埋在里面的还有四个坑，**每一个都是 git 的事，他一个也判断不了**：

1. **三个申请是叠着开的**：后两个都夹带了第一个的改动。他只要批了其中任何一个，第一个也会被悄悄一起带上线。
2. **后端测试在他电脑上全部跳过了**——电脑上没装数据库。说明里写着「要上服务器补跑」，没人补。
3. **第三条反馈停在了「方案讲明白」**：只写了「另开」，引用的那份决定记录压根没写出来。
4. **提交署名是电脑的默认名字**，事后看不出是谁做的。

更早一次，他自己在网页上点了合并。那个功能后来是技术负责人发另一个版本时被**顺带**带上线的。

**没有一个环节是他偷懒。** 是 AI 把只有它懂的事，交给了一个不懂的人去决定。

---

## 三、两份版本：怎么跟他讲

### 跟他说的

| 说法 | 意思 |
|---|---|
| **本地优化版本** | 正在改的那份。只在他自己电脑上能点，同事看不到。每个功能各一份，互不影响 |
| **正式版本** | 大家共用的那份。上线之后，同事看到的就是它 |
| **上线** | 把正式版本发出去，同事刷新就能用 |

需要打比方的时候，按他的业务现场现打。比如对做财务的人：「本地优化版本像你桌上的草稿，改坏了也不影响别人；正式版本像已经归档的那份，大家照它办事。」

### 给你的对照（别说给他听）

| 他听到的 | 实际是 |
|---|---|
| 本地优化版本 | 从**最新**主干开出来的功能分支，一个功能一条 |
| 正式版本 | 主干（通常叫 `main`） |
| 放进正式版本 | 合并进主干 |
| 上线 | 发布到服务器（各项目的发布方式不同，照项目自己的规矩） |

### 每个功能一份，不许叠

**每个本地优化版本都从最新的正式版本开，不许开在另一个还没做完的功能上面。** 叠着开，就是上面翻车里的第 1 个坑：他以为自己只放进去了一个功能，实际带进去两个。

功能 B 真的离不开功能 A 时，用业务话跟他说：「B 要等 A 做完才能开始」——然后先把 A 走完。

## 四、两个问题：什么时候问、怎么问

### 第一问：「这个功能做完了吗？」

**问之前，你自己先过这四条。** 有一条不满足，就还没到问的时候：

1. 他已经在自己电脑上**亲手点过**需求里的验收项（见 `docs/验收与交付.md`）
2. 测试**全部跑通**——「跳过」不是「通过」。电脑上缺东西导致跳过，先装齐再跑
3. 你自己先点过一遍，别让他当第一个发现问题的人
4. 这个功能要不要改数据库结构、改服务器配置？要的话，现在就告诉他上线时得找技术配合（见第八节）

问的时候，让他知道「做完了」意味着什么：

> 「这个功能做完了吗？做完了我就把它放进正式版本——放进去之后，下一次上线就会带上它，不管是谁点的上线。」

他说做完了 → 你把它放进正式版本，**然后马上问第二句**。

他说还没有 → 问他还差什么，接着改。

### 第二问：「现在上线吗？」

**你主动问，别等他开口。** 他不知道还有这一步——这正是翻车里「等你点头」的反面。

问的时候带上你的建议，并说清两件事：

- **上线后同事会看到什么变化**，尤其是会不会影响他们手上正在做的事
- **这次会不会顺带捎上别人做完的功能**（正式版本是大家共用的）

| ❌ 别这么问 | ✅ 这么问 |
|---|---|
| 「MR 已提交，未合并，等你点头。」 | 「日报锁定在你电脑上能点了，你试一下：昨天的日报点不动了。这个功能做完了吗？」 |
| 「要打 v1.0.2 的 tag 吗？」 | 「日报锁定已经放进正式版本了。现在上线吗？我建议下班后上：上线后同事就不能补昨天的日报了，白天上可能正好有人在补。这次还会顺带把小李做完的首页提醒一起带上。」 |

他说上 → 你发布，发完**自己去线上核一遍**，再回报「上线了，同事刷新就能用」。

他说先不上 → 停在正式版本。下次汇报时提醒他：「日报锁定还在正式版本里等上线。」

## 五、你全包的那些事

下面这些**一个都不问他**：

- **署名**：开工先确认提交用的是他自己的名字和邮箱，不是电脑默认名
- **开版本**：每个功能一条分支，从最新主干开
- **对齐**：别人放进正式版本的东西，及时同步到他正在改的版本里
- **放进正式版本**：他说「做完了」之后的合并，以及合并前的最后一次全量测试
- **冲突**：纯技术层面的冲突自己解决
- **发布、核对、回滚**：照项目的发布规矩走
- **收尾**：放进正式版本后，清掉用完的分支

### 唯一要问他的：改法打架

两个人改了同一处，而且**改法在业务上互相矛盾**——这不是技术问题，是业务问题，得他（或他们俩）拍板。

用业务话问：

> 「小王也改了日报：他的是过了零点就锁，你的是第二天中午才锁。留哪个？」

**不许问「有冲突，怎么处理」。** 他不知道冲突是什么，只能随便选一个。

## 六、报进度只用三句话

- 「还在你电脑上，同事看不到。」
- 「已经放进正式版本，等上线。」
- 「上线了，同事刷新就能用。」

**每次汇报都要落在其中一句上。** 一次动好几个功能时，逐个功能各落一句。

他最容易犯的错，就是把第一句听成第三句。所以**第一、二句里「同事看不到 / 等上线」这几个字不许省。**

---

## 七、没人替他看代码时，守门的是什么

他看不懂代码，也没有技术的人替他审。守门的只剩两样：**测试，和你自己。**

- **测试必须在他电脑上跑全。** 缺数据库、缺工具，你先装齐——这是 `AGENTS.md` 第一节「工具装好了没」的延续。**跑不全的测试等于没测**，而且会让他以为测过了。
- **上线后你自己去线上核。** 别等同事报错才知道。
- **出事了你主动说、主动回滚。** 先退回去，再告诉他发生了什么、影响了谁、怎么避免下次。

⚠️ 这不是银弹：测试只能拦住写过测试的地方。没人审代码，意味着测试没覆盖到的毛病会直接上线——**所以回滚要快，出事要早说。**

---

## 八、他点不了的事

下面这些，**不是他说一句「上线」就能做的**：

- 改数据库结构
- 改服务器配置
- 直接改线上的数据

遇到了就明说：

> 「这个功能上线前，要技术那边配合改一下数据库，我已经去找他了。」

然后你真的去找人。**项目里没有技术的人可找，就当场说清卡在哪、有什么办法**——别让它悄悄停在那。

---

## 九、一句话总结

**「做完了」「上线」这两句他说，其余都是你的事；每次开口，都让他知道同事现在用不用得上。**
