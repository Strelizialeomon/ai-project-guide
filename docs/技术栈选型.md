# 技术栈选型

`AGENTS.md` 第五节的展开。动手前读。

## 核心原则

**没有标准答案。** 同一件事有好几种做法，看需求、看手上有什么、看以后谁来维护。

**「技术栈不限，按项目情况定」不是一句客气话**——它是要求你真的去判断，而不是套一个熟悉的老配方。

⚠️ 但「不限」有个下限：**可以简单，不可以偏门。** 见第二节。

---

## 一、先摸真实情况，别凭印象拍脑袋

选之前先查这四样：

- **用户的电脑 / 服务器上已经装了什么** —— 已有的东西优先用，别让他为了你的选择再去装一堆
- **公司有没有现成在用的** —— 已有的数据库、已有的云账号、已有的域名。能用现成的就别新建
- **这东西以后谁来改、谁来维护** —— 是他自己？是技术同事？还是只有你？维护的人决定了能上多复杂的东西
- **要不要花钱、花多少** —— 有没有免费额度、超了怎么算

⚠️ **这里最容易犯的错是从训练直觉里拍脑袋。** 「我记得应该用 xx」不算依据。有真环境就去摸一手——能连的连上看看，能问的问清楚。

---

## 二、可以简单，不可以偏门

**这条比前面那条更容易犯，而且更隐蔽。**

「别一上来上重型方案」说的是**别过头**。这一条说的是**别走偏**。两件事，别混。

判据就一句：

> **这条路上，有没有别人走过？**

**走的人多** → 出问题搜得到答案、换个人（或换个 AI）来接得上、备份迁移看数据全都现成。

**走的人少、或者压根只有你走过** → 只有你懂。**你不在，这东西就死了。**

⚠️ 你的用户判断不了技术方案。**你选了偏门的，他看不出来。** 代价要等几个月才到——那时候已经不是在换方案，是在重做。

### 轻不等于偏门

这是最容易搞混的地方，画成表：

| | 在正道上 ✅ | 不在正道上 ❌ |
|---|---|---|
| **轻** | SQLite、本地小工具、导出个 Excel | **拿 JSON / CSV 文件当数据库**、拿文件名当主键 |
| **重** | Postgres、MySQL、对象存储 | 自研一套「轻量级存储引擎」、自研框架 |

**左右两列跟「轻 / 重」没有关系。** 别为了省事走右上那格，也别为了显得专业走右下那格。

### 花活的五种样子

自己对照：

1. **拿文件当数据库** —— JSON / CSV 存业务数据。没有并发、没有事务、写坏了全没
2. **自研轮子** —— 明明有现成的，自己写一个。**尤其是「现成的装不上」那种**——装不上就去查为什么装不上，不是自己造一个
3. **用刚出的新东西** —— beta 版、刚发三个月的库、小众语言。**你不是在选技术，你是在当第一个踩坑的**
4. **炫技式架构** —— 微服务、消息队列，用在三个人的内部工具上
5. **省掉正经的数据变更** —— 改字段靠手改数据文件，没有版本、没有回滚

第 1 条和第 2 条经常一起出现，长这样：

> 用现成的数据库 → 驱动装不上 → **那我自己写一个存储吧**

### 一个真实案例

> 来自一个财务工作台项目，细节做了匿名处理。

**第一版**：一个单文件 HTML，整个数据库序列化成 JSON，塞进浏览器的一个存储位。**换个电脑就没了。**

**第二版**：换成一台服务器上的后端，存储是自己写的——两百多行，追加日志 + 快照 + 冲突仲裁。

为什么不用现成的数据库？代码注释里的原话：

> 「本机验证环境里 better-sqlite3 原生模块直接段错误」

**一个驱动装不上，于是自己造了一个数据库。**

后果写在后来那份决策记录里，五条硬伤，条条都是现成数据库早就解决的：

- 写日志没有 fsync —— **掉电会丢最后几条写入**
- 冲突仲裁用**客户端自报的时间戳** —— 填未来时间的人赢
- 没有进程锁
- 一个大记录把十几个键折成一条
- 留痕只保留最近 5000 条，更早的**静默蒸发**

**第三版（现在）**：换回 MySQL。这次能查到真实数字。

- 数据迁移的代价：**0** —— 因为这系统还没上线、还没有真实数据
- 白写的代价：旧后端 **875 行代码 + 934 行测试**全部作废；新后端 **30 张表、728 行建表迁移、10018 行测试**；前端也因为废掉自己那套同步层而整个重建

**省下的是迁移，付出的是整个白写。**

### ⚠️ 「以后好换」不算理由

上面那个第二版，代码注释里还留了这么一句预告：

> 「以后真要换 Postgres / MySQL：只改这一个文件」

**这句话是幻觉。**

真换的时候，改的是表设计、测试、前端那一层——因为**文件存储的模型（一条条日志、快照）和数据库的模型（表、行）根本不是一回事**。模型不一样，上面每一层都得跟着重写。

所以：

- 说「以后只改这一个文件」的，**真换的时候改了一整层**
- 「先这样，回头再换」—— **回头的时候，成本不是「改一下」，是「重做一遍」**
- **拿「以后好换」当理由去选偏门方案，不成立**

### 确实要选偏门的时候

有，但很少。真到那时候：

- **必须明说**，别让他以为这是正常选择
- **说清代价**：什么时候会出问题、出什么问题、到时候怎么办
- **说清以后怎么换、换要花多大代价**——而且**别报乐观数字**

**「凑合」不是问题，「凑合着不说」才是问题。** 见最后一节。

## 三、给选项的规矩

**每个选项说清三样**：好处 / 代价 / 真实数字（钱 / 时间 / 风险）。

**别只报好的一面。** 把「不是银弹的地方」摆出来——这是你欠他的信息。

**拿不准就让他二选一。** 不要自己闷头选，也不要两个方案一起上。

**但也别把开放式技术问题甩给他。** 区别在这：

| ❌ 甩锅 | ✅ 给选项 |
|---|---|
| 「你想用哪个框架？」 | 「A 方案快但以后改起来麻烦，B 方案慢一点但好维护。我推荐 A，因为你这个东西大概不会再改了。」 |

框架的选择是**你的活**。他要拍板的是「快」还是「好维护」这种他能理解的取舍。

## 四、常见的几个岔路

| 岔路 | 怎么判 |
|---|---|
| **自己写 vs 用现成工具** | 先问「市面上有没有现成的」。能用现成的就别写——写出来就得维护，维护是要人命的 |
| **只我自己用 vs 同事也要用** | 只有他自己 → 可以先跑在他电脑上；要给别人用 → 必须有台一直在线的机器 |
| **买服务器 vs 用免费额度** | 先看用量和预算。免费的通常有额度限制或会休眠，**这些限制要提前跟他讲清楚**，别等用着用着发现打不开 |
| **数据库选哪个** | 数据量小、关系简单，就怎么简单怎么来。**别一上来上重型方案**——那是给自己找活。但**"简单"不等于"不用数据库"**：SQLite 就够小，拿 JSON 文件顶上就是偏门，见第二节 |
| **文件存哪** | 少量小文件可以跟数据放一起；图片、视频、大量附件就得上对象存储 |
| **要不要先做界面** | 可以，但做完必须说清「这只是门面，还差 A、B、C」。见 `四层模型.md` |

---

## 五、选完要说清的话

定下来之后，用一段大白话跟他交代：

- **这套东西要花多少钱**（哪怕答案是「暂时不花钱」）
- **以后谁来维护、坏了找谁**
- **有什么是现在凑合、以后得换的**

最后一条最重要。**「凑合」不是问题，「凑合着不说」才是问题。**
