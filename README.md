# ai-project-guide

给「不懂代码的业务人员 + 他的 AI」用的一套准则：怎么从一个想法，走到一个真正能用的项目。

## 这份东西解决什么

业务人员用 AI 做东西，最容易卡在同一个地方：**做出来一个能点开的网页，就以为做完了。**

点开一看确实漂亮。但——数据关掉就没了、同事打不开、附件传不上去、出了错不知道该找谁。这些不是「做得不够好」，是**从一开始就没人提过世界上还有这几层东西**。

这套准则就是补这一课：让带你的 AI 知道该判断什么、该问你什么、什么情况不许交活。

还有第二种卡法，样子不一样，根子相同：**张口就是「我要个看板」，但从没想过那些数从哪来。**

屏做得很漂亮，上面的数却是班组长每天下班前手工填的——**屏是真的，数是假的**。这不是「做得不够好」，是**只盯着看得见的那一头**。

这两种卡法底下是同一条原则。写在 `AGENTS.md` 开篇。

## 怎么用

把整个文件夹交给你的 AI（比如让 Claude Code 打开这个目录），说一句：

> 读一下这个目录，然后我们开始做项目。

`AGENTS.md` 是 AI 要遵守的准则，也是这套东西的唯一真相源。你自己也读得懂——因为它本来就是用大白话写的，只是执行责任在 AI 那边。

## 目录

| 文件 | AI 什么时候读 | 内容 |
|---|---|---|
| `AGENTS.md` | 每次开工前 | **准则主体**：总原则、判断依据、必须做的事、红线 |
| `docs/四层模型.md` | 判断要上哪几层时 | 「一个完整项目由哪几层组成」展开 |
| `docs/数据地基.md` | 他说要看板 / 监控 / 报表，或任何「我要看到某个数」时 | 「那些数从哪来」展开：入口、处理、存放、呈现在哪断的 |
| `docs/案例-正例与反例.md` | 拿不准该上几层、或想看怎么倒推时 | 四层全要的例子、一层就够的例子、一块二十多万大屏做坏的全过程 |
| `docs/需求梳理.md` | 开工前 | 怎么把想法问成一份写死的需求 |
| `docs/技术栈选型.md` | 动手前 | 用什么技术，谁说了算 |
| `docs/验收与交付.md` | 每一步做完时 | 怎么让你验收，交付时该交代什么 |

## 一句话

**没有凭空长出来的东西——看得见的结果，底下一定有一条链子撑着。**

具体到项目上：**「完整」不等于「层数多」，等于「该有的都有，不该有的不硬加」。**
